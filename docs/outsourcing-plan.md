# rembg-ui：P0–P3 与外包执行计划

基线：2026-09-15，源码提交 `88646de`，站点提交 `3d50002`。本计划分配待做工作，不代表已经实现或已发送给外部模型。外包由用户转发任务单；Codex 负责核心实现、集成与发布。

## 判断依据

当前浏览器版已支持 WASM 推理、原图对比、确认筛选和 ZIP 清单。`web/app.mjs` 仍把队列存在内存，并在新一轮处理时清空；只保存原名，没有可恢复的原始 File。`web/worker.mjs` 将推理和商品画布合成放在一次请求中；`web/delivery.mjs` 的确认只是布尔值，没有图像修订版本。`web/zip.mjs` 在内存中拼接多份数据。小样本成功不等于大图稳定或商用品质。

继续 extend 当前应用、复用 ONNX Runtime。暂不切 Rust/Pyodide，不另造推理引擎。已有 [Photoroom 批量工作流](https://www.photoroom.com/batch) 和 [Cutout Studio](https://github.com/jorgeadev/cutout-studio) 的项目/遮罩编辑先例，不能把基础批量抠图当作独占优势。gh 核验后者为 AGPL-3.0，仅作功能参考，不向本项目复制代码。社区的[批次编辑与导出反馈](https://www.reddit.com/r/photoroom/comments/1vfkwej/help_new_update/)只作为可靠性问题线索，不推导市场规模。

评分用失效代价、依赖关系和验证成本；目前缺少付费数据，不编造 ROI、模型能力排名或成本倍数。豆包用于文案/界面原型，用户指定的 DeepSeek/Flash 类模型用于规格明确的纯函数和测试；先验收小任务，再决定是否扩大权限。

## Codex 接手最难的部分

第一项为 **C01+C02：可恢复、可修订、可追溯的图像项目核心**。先完成小闭环再扩展：

1. 将状态与 DOM 分离；原图、透明底稿和导出图分别记录，给项目和图片稳定 ID。
2. 定义项目 schema、revision、图像 revision、reviewedRevision 和迁移规则；持久化 Blob，不保存临时 object URL。
3. 串行存储事务及版本冲突检查；处理中断可恢复，保存失败不得显示已保存；项目导入先验证，成功后才替换当前项目。
4. 将改规格合成与模型推理解耦；遮罩修改后递增图像修订号、清空旧确认。
5. 导出固定快照；正在修改或持久化失败不能静默导出错版本；ZIP、清单和图片名称相互校验。

Codex 独占修改：`web/app.mjs`、`web/worker.mjs`、`web/pixels.mjs`、`web/delivery.mjs`、`web/zip.mjs`、`web/build.mjs`、`web/package*.json`、`.github/workflows/`，以及后续 `web/core/`、`web/storage/`、`web/editor/`。正式 `web/index.html` 和部署仓库也由 Codex 集成。外包先不直接改这些文件。

拟定合同（待 Codex 实现后冻结，不是当前 API）：项目含 `schemaVersion/projectId/revision/settingsRevision/settings/items`；图片含 `id/sourceBlob/sourceName/maskBlob/cutoutBlob/imageRevision/reviewedRevision/reviewedSettingsRevision/status/error`。交付图可由底稿及规格生成。确认有效条件为 `reviewedRevision === imageRevision` 且 `reviewedSettingsRevision === settingsRevision`；事务用的 project revision 与规格 revision 分开，单纯勾选确认不能让其他确认失效。格式迁移和并发规则不能由各外包任务自行发明。

无需为了“并行”把同一核心问题拆给多个模型。最多同时推进这三个外包任务和一个核心任务；每单只交一个职责，失败最多返工一次，第二次仍不达标由 Codex 收回或缩小。

第二波必须等合同冻结：外包围绕已存在接口编写故障测试、更新帮助文档及接入批准的 UI 组件。第三波才考虑 B01/C05，支付与账户不分散给多个廉价模型拼接。

## 协作与合并规则

- 从本计划基线单独建分支/工作副本，每个任务独占目录；不要让多个模型直接操作同一个工作目录。当前桌面端存在未提交改动，不能 reset、清理、覆盖或顺手提交。
- 用户转发任务单和指定文件；不给 token、密钥或无权分享的客户原图。模型不自行注册账号、联系客户、购买服务、上传样本或发布网站。
- 返回任务 ID、基线提交、修改文件、实际测试命令与结果、截图/资料路径、未完成项。不能只回复“完成”。测试没有运行必须写明。
- 不加依赖、不迁移框架、不修改公开接口；发现需要越界时先返回建议，由 Codex处理依赖。
- Codex 检查来源/授权、差异、边界输入和真实 UI；只有合格结果才合并和部署。没有逐个外包任务直接推生产的权限。
- 工时与成本暂不精确承诺：先记录首个任务的调用费、人工转发时间、审查时间和返工次数。外包节省的是总交付成本，而不只是单次调用价格。

## 商业放行的测量方式

建议先做 30 张、至少 3 个目标品类的有权样本试验；该数量是内部试验起点，不是统计充分性保证。记录可直接交付率、中位返修时间、失败/恢复次数、首载耗时、支持耗时。先由用户确定可接受质量和支持成本，再决定收费门槛，不能事后把门槛改成测试结果。

第一轮成功标准：外包三份产物可独立验收，Codex 的恢复核心能通过中断/并发/版本一致性测试。此后再决定是否扩大外包规模或改模型。
